# 演示脚本（3–5 分钟）

目标：让看的人在 4 分钟里明白三件事——这是干什么的、它凭什么可信、几处关键取舍是按什么定的。

下面的操作全部可复现，命令都验证过。

## 一、演示前准备

1. 起服务并确认版本：

   ```bash
   python -m support_agent serve --port 8030
   python -m support_agent version     # 应报 1.4.0
   ```

   先手动问一个问题把模型链路预热一次（首次调用要加载向量模型，会多花几秒）。

2. **`.env` 绝对不要出现在画面里**。里面有 `LLM_API_KEY`。终端窗口把它挪到屏幕外，或先 `clear`。

3. 浏览器开两个标签：`http://127.0.0.1:8030/`（内建客户端）和 `http://127.0.0.1:8030/docs`（Swagger）。窗口宽度调到 1280 以上，别让代码块折行。

4. 录屏工具：Windows 用 `Win+G`（Xbox Game Bar）就够，或 OBS。**只录浏览器与终端窗口，不要录整个桌面**（桌面可能有其他文件）。

5. 关掉聊天软件通知。

## 二、分镜

### 第 1 段｜问题与定位（0:00–0:30）

画面：README 顶部，停在「光伏电站技术支持 Agent」和版本徽章。

旁白：

> 这是一个面向光伏电站运维的技术支持 Agent。现场排障的痛点不是没有资料，而是资料分散在十几份培训教材里，而且同一台设备常常有两版说法，值班的人没法判断该信哪一版。所以我做了这个项目：导入资料、带来源地回答问题、能查设备、能建工单，而且在它答不出来的时候会明确说答不出来。

### 第 2 段｜一条命令自检（0:30–1:00）

操作：终端跑

```bash
python -m support_agent doctor
```

画面停在输出上（7 行 OK）。

旁白：

> 先跑自检。它逐项报出配置、数据库里的文档与片段数、向量后端和维度、模型配置、检索参数、缓存和限流。**这一屏就能说明它不是个只能演示的空壳**：语料 20 份文档、212 个片段，向量用的是本地 ONNX 模型，512 维。

> 顺带说一句，`doctor` 会真的读写一次缓存再报结果，所以「配了 Redis 但连不上」这种情况它会如实报出来，而不是照配置念一遍。

### 第 3 段｜知识问答带引用（1:00–1:50）

操作：在内建客户端里问

> 绝缘阻抗故障怎么定位？

画面：回答 + 下方引用列表。滚到引用处停一下。

旁白：

> 回答带来源引用，每一条都能翻回原文。要注意左下角这几个字段：`status` 是 `completed`，`answer_source` 是 `knowledge`——**这两个值是服务端判的，不是模型自己说的**。

> 这一屏还出现了版本并列提示。因为资料里有 V2.0 和另外一册两版说法，分数接近却版本不同时，它不会替用户揉成一个答案，而是两份并列交回去，让现场按设备版本确认。**这在运维场景里比给一个确定答案更重要**。

### 第 4 段｜答不出来的时候怎么办（1:50–2:40）

操作：问第一个问题

> 怎么考驾照？

画面：`status=needs_clarification`，请补充型号或现象。

旁白：

> 这是个刻意的设计。项目最早的做法是设一个分数阈值，低于阈值就拒答。后来实测发现**做不到**：库内和库外问题的分数区间在词汇和语义两个维度上都重叠——语义向量下库外最高 0.604、库内最低 0.505。阈值怎么定都会误伤一批。

> 所以改成两个语料范围判据，而且**放在调用模型之前**。原因是实测模型遇到明显跑题的问题时压根不会去调检索工具，它直接凭「我是光伏助手」拒答，服务端那句兜底永远等不到。

> 判为跑题之后也不拒答，而是请用户补一句型号或现象。判据是词汇层面的近似，口语化的真问题也会撞上它，一律拒答会把答得出的问题也推走。这条取舍和它的代价都写在架构文档里。

操作：接着问

> SN-2024-000123 这台设备现在什么状态？

画面：`answer_source=tool`，返回设备档案。

旁白：

> 设备查询走工具，不查这份资料。所以带设备序列号的问题会在判据那里被豁免——**判据问的是「这个问题属于这份资料吗」，拿同一把尺子去量工具类问题会量错**，这是加豁免时踩出来的。

### 第 5 段｜写操作要人工确认（2:40–3:30）

操作：发一句建工单的请求。

画面：`status=pending_confirmation` + 返回的 `confirmation_token`。复制令牌。

终端：

```bash
curl -X POST http://127.0.0.1:8030/tickets \
  -H "Content-Type: application/json" \
  -d '{"confirmation_token":"<粘贴>","user_id":"demo"}'
```

第一次 → `201`。原样再发一次 → `409 确认令牌已经使用`。

旁白：

> 建工单是写操作，模型只能提出申请，服务端在循环里就把它拦下，然后签一张十分钟有效的令牌。

> 令牌有四道闸：验签、有效期、用户归属、只能使用一次。第四道闸背后是一张以令牌哈希为主键的表——**判重靠数据库的唯一约束，不是先查再写**。先查再写在并发下会有时间窗，两个请求都能查到「没人用过」，同一张令牌能建出两条工单。

> 验签排在判重之前也是有意的：反过来的话，一张被篡改的令牌会被判成「已使用」，从返回码就能反推出这张令牌存在过。

### 第 6 段｜工程质量（3:30–4:00）

操作：终端

```bash
python -m pytest -q
```

可以等它跑完，也可以直接 Ctrl+C 后说数字。

旁白：

> 199 个用例覆盖检索、工具安全、用户隔离、确认流程和缓存降级。另外还做了一件我认为最值得说的事：**评测不是自己写一套判定，而是复用线上那条链路的判定代码**，分检索、工具选择、最终回答三层，声明了哪层就评哪层。这样「评测通过」和「线上行为正确」说的是同一件事。

> 切块参数也是做过对照的：300/50 明显更差，片段数翻倍而 hit@1 从 0.700 掉到 0.625；1200/150 与 700/100 的差距在噪声内。所以维持 700/100，理由是「细的明显更差、粗的没有可证实的增益」。

### 第 7 段｜收尾（4:00–4:20）

画面：回到 README 的「仓库导航」。

旁白：

> 项目还有明确的已知边界：MCP Server 目前是旁路能力，没接进主链路；pgvector 只做了列类型映射，没有接 ANN 索引——因为打分用的 IDF 权重依赖全语料词频，只取近邻候选就算不出来。这些和它们的修复顺序都写在文档里，没有藏。

## 三、三条纪律

- **不夸大**：说「在噪声内」就不要说「更好」。数字一律用能当场跑出来的那些。
- **不念功能清单**：每讲一个功能，讲它解决的具体问题，以及你放弃了什么。
- **停顿留给画面**：说到 `status`、`409`、`hit@1` 这些值时让画面停一下，观众要看清。
